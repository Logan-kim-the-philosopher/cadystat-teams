# Codyspace SSO 연동 계약 초안

- 상태: **연동 담당자 검토용 제안**
- 범위: Teams 웹 앱의 로그인, 세션, 사용자 식별, 역할 연결
- 제외: 운영 DB 적용 및 배포 설정 변경

이 문서는 Codyspace SSO 구현 세부를 이미 알고 있다고 가정하지 않는다. issuer URL, client ID, callback 주소, 실제 claim 이름 등은 Codyspace SSO 담당자가 확인해 확정해야 한다. 구현 전에 이 문서의 **확인 필요** 항목을 함께 결정한다.

## 1. 목표와 책임 경계

- Codyspace SSO는 사용자의 인증과 로그인 세션을 제공한다.
- Teams 앱은 SSO 사용자를 Teams 조직 데이터에 연결하고 Teams 안의 권한을 판정한다.
- 인증 여부만으로 관리자 권한을 주지 않는다.
- 브라우저에서 Teams 페이지와 Teams API를 사용할 때 로그인한 사용자 신원을 서버가 확인할 수 있어야 한다.
- 프런트엔드가 보낸 사용자 ID, 이메일, 역할 값을 권한 판단의 근거로 신뢰하지 않는다.

## 2. 권장 로그인 흐름

Codyspace가 표준 OIDC 제공자라면 서버 측 **Authorization Code Flow**를 우선 사용한다. SPA에 client secret을 두지 않고, 가능한 경우 PKCE를 함께 사용한다.

1. 비로그인 사용자가 Teams의 보호된 페이지/API에 접근한다.
2. Teams 서버가 state와 nonce를 생성·저장하고 Codyspace 로그인으로 보낸다.
3. Codyspace가 등록된 callback으로 authorization code를 돌려준다.
4. Teams 서버가 code를 검증/교환하고 서명·issuer·audience·만료·nonce를 확인한다.
5. Teams 서버가 확인된 사용자 식별자와 만료 정보를 서버 세션에 저장한다.
6. 로그아웃 때 Teams 세션을 폐기한다. Codyspace SSO 전역 로그아웃 지원 여부는 별도로 확인한다.

게이트웨이가 OIDC 대신 인증된 identity를 전달한다면, 임의 HTTP 헤더를 읽는 방식은 허용하지 않는다. 그 신원이 위조 불가능한 서명 토큰으로 검증되거나, 게이트웨이에서만 접근 가능한 네트워크 경계와 요청 서명으로 검증되는 계약이 필요하다. 원본 앱 서버에 직접 접근해 인증을 우회할 수 없어야 한다.

## 3. 세션 및 웹 보안 요구사항

- 세션은 서버에서 검증·관리한다. 브라우저 저장소의 사용자 입력 값을 인증으로 간주하지 않는다.
- 세션 cookie는 `HttpOnly`, `Secure`(HTTPS), 적절한 `SameSite` 설정을 사용한다.
- 로그인 callback에서 state/nonce를 검증하고 재사용을 거부한다.
- 로그아웃은 세션을 무효화하고 cookie를 제거한다.
- 인증되지 않은 페이지 요청은 Codyspace 로그인으로 이동시키고, API 요청은 JSON `401`을 반환한다. API가 HTML 로그인 페이지를 성공 응답처럼 반환하지 않게 한다.
- 로그인 후 돌아갈 경로는 같은 서비스 내부의 허용된 상대 경로만 허용한다.
- 모든 변경 API는 세션 기반 CSRF 방어를 적용한다. 기존 same-origin 검사만으로 인증·권한을 대체하지 않는다.
- 접근/토큰/세션 관련 로그에 authorization code, access/refresh token, cookie 원문을 남기지 않는다.

## 4. Teams 사용자와 조직 구성원 연결

권장 식별 순서:

1. SSO 응답에서 변하지 않는 `sub`(subject)를 사용자 기본 식별자로 사용한다.
2. 최초 연결은 Codyspace가 **검증한 이메일**과 조직도 구성원의 이메일을 trim + 소문자 정규화 후 비교한다.
3. 정확히 하나의 구성원만 일치하면 사용자와 구성원을 연결한다. 중복 이메일, `email_verified`가 없거나 false, 이메일 누락, 일치 구성원 없음은 자동 연결하지 않는다.
4. 자동 연결 결과는 서버가 검증하고, 이후에는 가능한 경우 저장한 SSO `sub`를 사용한다. 이메일 변경 시 계정을 임의의 다른 구성원에 자동 재연결하지 않는다.
5. 이메일이 비어 있거나 일치하는 SSO 계정이 없는 구성원은 조직도에는 남기되 계정 연결 전까지 **조회 전용**이다.

**확인 필요:** Codyspace가 `sub`, 검증된 이메일, `email_verified`, 이름을 제공하는지와 이메일 변경/중복 처리 계약.

## 5. 역할 및 권한 정책

인증된 SSO 사용자와 조직도 구성원 매칭 상태에 따라 서버가 다음 권한을 계산한다. UI에서 버튼을 숨기는 것은 보조 표시일 뿐이며 각 API에서 같은 정책을 강제한다.

| 사용자 | 회의록 | 조직도 | 티켓 |
|---|---|---|---|
| 비로그인 | 접근 불가 | 접근 불가 | 접근 불가 |
| 로그인했으나 조직도 구성원 미연결 | 조회 | 조회 | 모든 티켓 조회만 |
| 연결된 팀원 | 조회 | 조회 | 모든 티켓 조회·변경 |
| 연결된 팀장 | 조회 | 자기 팀 범위 관리 | 모든 티켓 조회·변경 |
| Teams 관리자 | 조회·생성·수정·삭제 | 전체 관리 | 모든 티켓 조회·변경 |

- **회의록:** 모든 로그인 사용자 조회 가능, 변경(작성/수정/삭제/댓글 포함)은 Teams 관리자만 가능.
- **조직도:** 관리자와 팀장이 관리 가능. 팀장은 자신의 팀 범위로 제한한다. 세부적으로 팀장에게 팀 생성/삭제까지 허용할지는 확인 필요하며, 기본 제안은 자기 팀의 구성원·팀 정보 편집만 허용하는 것이다.
- **티켓:** 연결된 구성원인 관리자·팀장·팀원은 역할별 차등 없이 모든 티켓을 조회하고 변경할 수 있다. 비연결 계정은 조회만 가능하다.
- **기본 거부:** 사용자를 판별할 수 없거나 구성원/팀장 연결이 모호하면 변경을 허용하지 않는다.

## 6. 관리자 bootstrap 및 역할 원천

- 최초 Teams 관리자는 운영자가 배포 설정으로 지정한 **초기 관리자 이메일**로 bootstrap한다.
- bootstrap 이메일은 SSO의 검증된 이메일과 정규화 후 비교한다. 프런트엔드 파라미터나 첫 로그인 순서로 관리자를 정하지 않는다.
- bootstrap 설정이 빠졌거나 매칭이 모호하면 접근을 거부하고 서버 로그에는 원문 대신 설정 누락 상태만 기록한다.
- 최초 관리자 이후 관리자 추가/해제의 단일 권한 원천과 운영 절차는 별도 확정이 필요하다. SSO 그룹/claim이 자동 관리자 권한을 부여하는 방식은 합의 전까지 사용하지 않는다.

## 7. API 경계

### 브라우저 API

`/api/teams/*`는 SSO 세션을 요구하고, 각 API가 회의록/조직도/티켓 권한표를 서버에서 검사한다. 로그인 여부만 확인하고 모든 변경을 허용해서는 안 된다.

### 에이전트 API

현재 합의된 기대는 `/api/v1/*`도 Codyspace SSO 보호 경계 안에 두고, 기존 API key를 추가 검증 수단으로 유지하는 것이다. API key는 SSO 인증이나 사용자 권한을 대체하지 않는다.

사람의 브라우저 로그인은 비대화형 에이전트에 적합하지 않으므로 다음 중 실제 운영 방식은 Codyspace 담당자와 확정해야 한다.

- Cloudflare Access 등 게이트웨이가 지원하는 service token / workload identity와 기존 Teams API key를 함께 사용
- 또는 승인된 machine-to-machine OAuth client와 기존 Teams API key를 함께 사용

API 접근에서는 게이트웨이 신원, Teams API key의 역할/소유 범위, 호출 가능한 endpoint, 만료·폐기·회전, idempotency/rate limit을 각각 검증한다. 게이트웨이 서비스 자격증명을 사용자 세션으로 취급하거나 API key만으로 SSO 경계를 우회하지 않는다.

## 8. 미리보기 및 운영 경계

- 로컬 목업 모드에서는 테스트용 가짜 identity를 명시적으로 켤 수 있지만, 기본값과 배포 빌드에서는 비활성화한다.
- SSO 설정 누락 시 운영에서 익명 공개 모드로 조용히 fallback하지 않는다.
- 개발/테스트 DB에서 migration과 접근 정책을 검증한다.
- 이 문서 작성만으로 운영 DB 변경, 운영 secret 추가, Cloudflare/Codyspace 설정 변경은 하지 않는다.

## 9. Codyspace SSO 담당자와 확정할 항목

1. SSO 방식: OIDC issuer/discovery URL 또는 gateway assertion 계약.
2. 앱 등록: client ID/secret 보관 방식, 허용 callback/logout URL, 환경별 설정.
3. 사용자 claims: `sub`, 이메일 검증 여부, 이름, 계정 비활성화/로그아웃 신호.
4. callback 및 세션 수명·갱신·로그아웃·재인증 동작.
5. Gateway/Cloudflare Access에서 웹 로그인과 비대화형 API service identity를 함께 지원하는 방식.
6. 초기 관리자 bootstrap 이후 관리자 권한의 부여·회수 책임자와 저장 위치.
7. 이메일 중복·변경·미인증·미매칭 계정의 처리 절차.
8. Codyspace SSO 담당자가 제공할 로컬/검증 환경, 테스트 계정, 재현 가능한 검증 절차.

위 항목과 보안 검토가 합의된 뒤 코드와 migration을 확정한다. 특히 production-facing auth 및 권한 코드는 이 계약의 endpoint/claim을 확인하기 전 추정 구현하지 않는다.
